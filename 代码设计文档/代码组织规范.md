# 代码组织规范

> 配套文档：`命名规范.md`（文件/目录怎么起名）、`前端架构设计规范.md`（业务域怎么切分）。
> 本文档只回答一个问题：**什么时候该拆文件/模块，什么时候不该拆。**

## 拆分判定

**职责单一优先于行数。** 300 行职责清晰的纯函数文件，优于 150 行混杂了请求、状态、渲染的组件。

行数只是症状，职责混杂才是病因。判断时永远先问"这个文件是不是在同时做两件不相关的事"，再看行数。

### 参考红线

- 纯逻辑文件：**400 行**
- 含 JSX / 模板的文件：**400 行**
  - 模板行密度低（闭合标签、缩进占行），判断时**先扣掉模板部分看逻辑行数**；
  - 例：一个 500 行的组件，如果 JSX 占 300 行、逻辑只有 200 行，不算超红线。

红线是「停下来审视」的触发点，**不是禁令**。

### 审视信号（接近或超过红线时逐条检查）

1. **导出 > 5 个且彼此无调用关系** —— 说明这里堆了几个独立能力；
2. **import 明显分成互不相关的几组** —— 例如同一文件既 import 时间格式化、又 import 剪贴板、又 import 外链打开；
3. **存在两处以上无关修改点** —— "改这个功能要动这里，改那个功能也要动这里"，且两处互不相关；
4. **改动扩散** —— 同一文件在近期提交里频繁被改，且改的是不同功能。这是职责混杂最硬的证据（`TaskPanel` 修复前 1315 行、每次新功能都改它，就是这种情况）。

### 审视结果

- **职责仍单一** → 保留，并在文件头注释说明"为什么这么大是合理的"。
  - 例：`AgentFlow.tsx` 575 行 = 完整的执行步骤流渲染，拆开需要向子组件传十几个 props，反而更难维护。
- **职责混杂** → 按能力拆，拆完检查父文件是否只剩组装逻辑。
  - 例：`TaskPanel.tsx` 1315 → 533 行，按功能抽出 6 个 hook、2 个组件，父文件只剩组装与布局。

### 反向信号：可能拆过头了

拆分的目的不是"每个文件都小于 400 行"，而是"改一个功能只进一个目录"。出现以下情况说明拆过头：

- 子文件只有 20–50 行，且只被一个父文件使用；
- 拆分后 props 超过 10 个；
- 状态需要跨 3 层传递；
- 为了复用 3 行代码建了一个新文件。

拆过头和拆不够一样有害：文件跳转成本、props 穿透、调试链路变长，都是真实代价。

### 判定流程

```text
文件变大
  ↓
是否接近/超过 400 行？ ──否──→ 继续用，不必处理
  ↓ 是
逐条检查 4 个审视信号
  ↓
职责仍单一？ ──是──→ 保留 + 注释说明理由
  ↓ 否
按能力拆分（优先抽 hook / 纯函数，其次拆组件）
  ↓
父文件是否只剩组装逻辑？ ──是──→ 检查反向信号，避免拆过头
```

## 目录深度与命名形态

### 深度

- 建议 **≤ 4 层**（从 `src/` 算起）。
- 超过 4 层时先问"是不是业务域没切开"，而不是直接禁止。
- 确有必要的（如渲染器的子模型）在首处注释说明理由。
- 现状例外：`src/modules/pet/renderers/glb-model/ears`（5 层），属合理结构。

### 复数 / 单数（按含义，不按数量）

- 装多个同类东西的**集合目录用复数**：`components/`、`hooks/`、`attachments/`、`panels/`；
- 表示一个**业务概念的目录用单数**：`conversation/`、`task/`、`input/`、`model-status/`；
- **单文件一律单数**：`button.ts`，不写 `buttons.ts`。

## 迁移策略（存量怎么整理）

- 新文件必须遵守本规范与命名规范；
- 老文件在被修改时顺手改名，不单独排期；
- **重命名 / 移动必须与逻辑改动分开提交**（这是 review 能否看懂的关键）；
- 重命名批次大小看改动性质，不设文件数上限；
- 每次重命名后跑 `typecheck` + `build` + 相关离线测试，再重启应用验证。

## 文档版本

- 设计 / 规范类文档在文首维护：**最后更新日期、更新人、一行变更摘要**；
