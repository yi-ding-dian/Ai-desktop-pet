# 编码代理接入设计（DeepSeek Harness / ACP）

> 日期：2026-10-23　状态：V1 已实现（待真机任务验收）
>
> 一句话：小兔不自己拿 shell，而是把“写代码/跑测试”的活外包给本机的
> DeepSeek Harness（`dsh`），通过它的 ACP 接口逐步转发进度、逐条征求授权。

## 1. 背景与目标

V1 的系统巡检只读、清理白名单、删除二次确认，能“看”不能“改”。用户希望小兔
能帮忙写代码、跑测试并一直做到完成。直接给宠物加 shell/写文件会破坏现有的安全
边界（只读巡检 + 敏感操作确认）。因此选择**外接一个成熟的编码代理运行时**：

- 编码循环、工具集、沙箱、权限策略由外部 harness 负责；
- 小兔只做四件事：**发起任务、转发每一步、转发授权请求、中止任务**；
- 宠物本体仍然没有任意命令执行能力。

目标 harness：[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)
（`dsh`，MIT，TypeScript，developer preview）。选它是因为它自带标准 ACP 服务
（`dsh --profile acp`），协议面刚好覆盖“每步事件 + 权限确认”。

## 2. 非目标

- 不自研 Agent Loop、工具集、沙箱；
- 不让宠物直接执行 shell、写文件、改注册表；
- 不做多任务并行（同一时间只允许一个编码任务）；
- 不做代码 diff 审阅 UI、git 提交、PR 创建（V2 再议）；
- 不把 dsh 的 Web UI 内嵌进宠物（只作为排障入口）。

## 3. 总体架构

```
用户：「帮我改 xxx 功能」
        │
        ▼
后端 LLM 决定调用 delegate_coding（frontend 型工具，prepare 校验）
        │  WS tool_call
        ▼
宠物窗渲染层 tools/index.ts 执行器
        │  window.pet.coding.start({ task, workspace })
        ▼
Electron 主进程 coding 域
        ├─ 工作区授权（用户目录选择 / 路径校验 / 保护目录拒绝）
        ├─ 确认气泡（工作区 + 任务摘要）
        ├─ 复用宠物 Key：GET /internal/llm-key → DEEPSEEK_API_KEY + 隔离 DSH_HOME
        ├─ spawn `dsh --profile acp`（stdio JSON-RPC）
        ├─ initialize → session/new → session/prompt
        ├─ session/update        → CodingState.steps → 工作窗步骤流
        ├─ session/request_permission → 确认气泡 → allow_once / cancelled
        └─ session/cancel / taskkill → 中止与进程树回收
```

依赖方向：`coding` 域只依赖 `bubble`（确认气泡）、`work`（自动打开工作窗）、
`system/path-safety`（保护目录），不反向依赖 `ipc` 或渲染层。

## 4. ACP 协议接入点

传输：stdio，newline-delimited JSON-RPC 2.0。客户端**不声明任何可选能力**
（`clientCapabilities: {}`），即不提供文件系统、终端、elicitation —— 所有工具
由 dsh 子进程自己执行。

| 方向 | 方法 | 用途 |
|---|---|---|
| 客户端 → agent | `initialize` | `{protocolVersion: 1, clientCapabilities: {}}` |
| 客户端 → agent | `session/new` | `{cwd: 绝对工作区, mcpServers: []}` → `{sessionId}` |
| 客户端 → agent | `session/prompt` | `{sessionId, prompt: [{type:'text', text: 任务}]}` → `{stopReason}` |
| 客户端 → agent | `session/cancel` | 通知；随后仍以进程回收兜底 |
| agent → 客户端 | `session/update` | 通知：消息/思考/工具调用/计划 |
| agent → 客户端 | `session/request_permission` | 请求：一次性 allow/reject 选项 |

`session/update` 到步骤流的映射：

| `sessionUpdate` | 处理 |
|---|---|
| `agent_message_chunk` | 追加到当前“回复”步骤（同一步骤内累积文本） |
| `agent_thought_chunk` | 追加到当前“思考”步骤（默认折叠） |
| `tool_call` | 新建工具步骤：`toolCallId / title / kind / status / rawInput` |
| `tool_call_update` | 按 `toolCallId` 更新状态与标题 |
| `plan` | 新建一条“计划”步骤（只展示条目标题） |
| 其它 | 忽略（保留扩展空间） |

权限请求应答：

- 允许：选择第一个 `kind` 为 `allow_once` 的选项（**永不自动选 `allow_always`**）；
- 拒绝 / 没有可用选项：返回 `{outcome:{outcome:'cancelled'}}`，子进程不会继续该操作。

## 5. 安全模型

1. **工作区授权**：只允许绝对路径、必须真实存在且是目录、拒绝盘符根、拒绝
   UNC、拒绝小兔自己的安装/数据/日志目录（复用 `protectedPathReason`）。
   用户没给路径时弹系统目录选择框，选完仍要确认气泡。
2. **启动确认**：每次任务开始都弹气泡，展示工作区与任务摘要；取消则什么都不做。
3. **权限转发**：dsh 的每个风险操作（写文件、执行命令等）都会发
   `session/request_permission`，主进程转成气泡；用户拒绝即 `cancelled`。
4. **进程隔离**：`mcpServers: []`，不声明 fs/terminal 能力，编码代理只能在
   自己的子进程里干活；结束/取消/超时都按**进程树**回收（Windows
   `taskkill /PID <pid> /T /F`）。
5. **审计**：任务开始、每次授权决定、任务结束追加写入
   `userData/logs/coding-audit.jsonl`（单行 JSON，含时间、任务摘要、工作区、
   决定、结束原因；不记录文件内容）。
6. **不碰密钥**：只透传调用方环境里已有的 `DEEPSEEK_API_KEY`；不读取、不写回
   宠物设置里的密钥。

## 6. 工具契约

工具名：`delegate_coding`（executor = frontend）。

| 参数 | 类型 | 说明 |
|---|---|---|
| `task` | string | 任务描述，1–2000 字；必须来自用户本轮请求 |
| `workspace` | string | 可选，绝对目录；不给则由用户在工作区选择框里选 |

`prepare(args, user_text)`：

- `task` 为空/超长 → 拒绝；
- `workspace` 给了但不是绝对路径，或**没有出现在用户本轮原话里** → 拒绝
  （防止模型自行拼路径或受网页/文件内容诱导）；
- 通过则原样派发；主进程再做存在性、保护目录等二次校验。

模型侧规则（`capabilities.md`）：

- 只有用户明确要求“写代码/改代码/跑测试/修 bug/做功能”时才调用；
- 任务描述要具体（目标、验收方式），不要把自己的推测写成用户需求；
- 调用后不要声称“已完成”，完成与否以工作窗步骤流和最终总结为准。

## 7. 状态与事件模型

主进程持有唯一的 `CodingState`（步骤上限 500 条，单条 detail 上限 2000 字），
变化时**整份快照**推给宠物窗与工作窗（节流 250ms），渲染层不做增量合并。

```ts
type CodingStatus =
  | 'starting' | 'running' | 'waiting' | 'done' | 'cancelled' | 'error'

interface CodingStep {
  id: string
  kind: 'thought' | 'message' | 'tool' | 'plan' | 'system'
  title: string
  detail?: string
  status: 'running' | 'done' | 'failed'
  at: number
}

interface CodingState {
  taskId: string | null
  status: CodingStatus
  task: string
  workspace: string
  steps: CodingStep[]
  summary?: string
  error?: string
  startedAt?: number
  endedAt?: number
}
```

## 8. IPC 与 preload

| 通道 | 方向 | 说明 |
|---|---|---|
| `coding:start` | invoke（宠物窗） | `{task, workspace?}` → `{ok, message, taskId?}` |
| `coding:cancel` | invoke | 中止当前任务 |
| `coding:get-state` | invoke | 工作窗初始化时取快照 |
| `coding:state` | 主进程推送 | 状态快照（宠物窗 + 工作窗） |

preload 暴露 `coding.start / cancel / getState / onState`。

## 9. UI

工作窗“对话”页顶部出现「编码任务」面板（仅任务存在时渲染）：

- 标题行：任务摘要 + 工作区 + 状态徽标 + 中止按钮；
- 步骤列表：最多显示最近 200 条，工具步骤带状态点，思考默认折叠；
- 结束后保留结果供回看（直到下一次任务开始），可手动收起。

任务启动时自动打开工作窗；宠物窗只通过气泡说一句“进度在工作窗里”。

## 10. 生命周期与失败处理

- 启动超时：`initialize` 30s；`session/new` 30s；
- 任务总时长上限：默认 30 分钟（常量，可后续做成设置）；
- 取消：`session/cancel` → 关闭 stdin → 3s 宽限 → 进程树强制终止；
- 子进程退出：状态置 `error`，附最后 20 行 stderr（裁剪、去密钥样式）；
- 找不到 `dsh` 或启动失败：返回可操作的中文提示（安装/升级/配置），不重试；
- 重复调用：已有任务在跑时拒绝并提示先中止。

## 11. 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `PET_DSH_COMMAND` | 自动探测 | 自定义可执行文件（含路径）；参数固定 `--profile acp` |
| `PET_DSH_HOME` | 用户默认 `~/.dsh` | 传给子进程的 `DSH_HOME` |
| `DEEPSEEK_API_KEY` | 进程环境 | 存在则透传给子进程 |

命令探测顺序：`PET_DSH_COMMAND` → **应用内 runtime** → PATH 上的 `dsh` / `dsh.cmd`
（版本 ≥ 0.2.0）→ `npx -y @deepseek-ai/dsh@0.2.1-rc.2`。若装的是旧版（没有
`acp` profile），自动回退 npx；仍失败时错误信息里会提示去设置页安装。

### 11.1 运行时检测与安装（设置页，2026-10-23）

「设置 → LLM → 编码代理」提供：

- **检测**：四态 `ready / npx-only / outdated / unavailable`，附带版本、来源、安装目录；
- **安装**：`npm install --prefix <runtimeDir> --no-audit --no-fund --no-progress
  @deepseek-ai/dsh@0.2.1-rc.2`，输出流式显示，可取消，15 分钟超时；
- **卸载**：只删除应用自己的 `dsh-runtime/`，不动系统全局 dsh；删除前原生确认框；
- 安装/卸载前若有任务在跑，直接拒绝。

安装目录（用户级，无需管理员）：

| 平台 | 路径 |
|---|---|
| Windows | `%LOCALAPPDATA%\ai-desktop-pet\dsh-runtime`（刻意不用 Roaming，避免同步几百 MB） |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/ai-desktop-pet/dsh-runtime` |
| macOS | `~/Library/Application Support/ai-desktop-pet/dsh-runtime` |

原则：**不静默安装**，必须用户点按钮；不写全局 npm，不动系统目录；失败保留日志可重试。

实测（Windows 11 / npm 11 / 0.2.1-rc.2）：613 个包、约 **838MB**、耗时约 4 分钟；
装完 `.bin/dsh.cmd --version` 正常。设置页已标注体积与耗时预期。

### 11.2 复用宠物 LLM Key（2026-10-23）

设置页「编码代理」里的开关，默认开启。开启时启动任务会：

1. 主进程向后端 `GET /internal/llm-key` 取 Key（`127.0.0.1` + **独立内部 token**）；
2. 检查宠物 LLM 的 `base_url` 是否是 DeepSeek 域名——不是就放弃复用，改用 dsh 自己的凭据，
   并在步骤流里说明原因（避免把 Kimi/OpenAI 的 Key 塞给 DeepSeek）；
3. 把 Key 只放进 dsh 子进程的 `DEEPSEEK_API_KEY` 环境变量，并设置**隔离的 `DSH_HOME`**：
   - dsh 的凭据优先级是「存储文件 > 启动环境」，用户自己的 `~/.dsh` 里可能存着失效旧 Key；
   - 隔离 home 位于应用数据目录（`.../ai-desktop-pet/dsh-home`），里面没有旧凭据，
     环境变量才会生效。

安全约束：

- 内部端点使用 **另一个 token**（`PET_INTERNAL_TOKEN`），与渲染层持有的 WS token 分开；
  渲染层永远拿不到内部 token；
- Key 不落盘、不进日志、不进 WS/IPC，只在主进程内存与子进程环境变量里；
- 端点只绑 127.0.0.1，响应 `Cache-Control: no-store`；
- 关闭开关则完全回到 dsh 自己的配置。

已验证：全新 `DSH_HOME` + 假 Key 启动，认证失败的报错里显示的是**假 Key 的尾号**，
证明环境变量优先于任何存储凭据；内部端点用 WS token 访问返回 403。

凭据：默认**复用宠物 LLM 的 DeepSeek Key**（见 §11.2）；关闭开关或宠物用的是
其他服务商时，回退到 **dsh 自己的凭据**（隔离 `DSH_HOME` 或用户自己的 `~/.dsh`）。
若报 `Authentication Fails`，说明当前生效的那把 Key 无效：改「设置 → LLM」里的 Key
（复用开）或在 dsh 里更新（复用关）。

## 13. 测试

- 单元：JSON-RPC 分帧、错误响应、双向 request；ACP 事件映射；命令解析
  （Windows `.cmd` / POSIX / env 覆盖）；工作区校验；步骤裁剪。
- 集成：`fake-acp` 子进程脚本模拟 dsh，跑通“启动 → 步骤 → 权限 → 完成”与
  “取消 → 进程退出”两条链路（不依赖真实模型）。
- 后端：`delegate_coding` 注册、prepare 接受/拒绝、工具总数更新。
- 手工：本机 `dsh`（≥0.2.1）跑一条真实任务，确认步骤流与确认气泡。

## 14. 验收标准

1. 用户说“帮我改一下 D:\x 里的 y”，宠物能调用 `delegate_coding`，工作窗自动
   打开并逐条显示步骤；
2. 编码代理要写文件/执行命令时，宠物弹确认气泡；拒绝后该操作不发生；
3. 点“中止”后子进程树被回收，状态显示“已取消”；
4. 未安装 dsh / 版本过旧 / 工作区非法时，给出可操作的中文提示；
5. 设置页能检测出「已就绪 / 只能 npx / 版本过旧 / 不可用」，并能一键装到应用目录、
   流式看到进度、取消、卸载；安装后可被任务直接使用；
6. 全程宠物本身不执行任何 shell 命令，审计日志有据可查。

## 15. 风险与后续

- dsh 是 developer preview，会破坏性变更 → 锁定版本，协议层做宽松解析；
- 打包体积：目前依赖用户本机 Node/dsh；V2 可探测并引导安装，或随包分发
  固定 runtime；
- 暂不提供 diff 审阅与 git 回滚 → V2 增加“每步 checkpoint + 结束出 diff”；
- 权限气泡信息量有限（标题 + 参数摘要）→ V2 在工作窗里展示完整工具调用卡片。
