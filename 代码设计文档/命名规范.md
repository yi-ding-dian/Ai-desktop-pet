## 文件/目录命名规范

- 工具强制 > 生态惯例 > 本规范 > 历史遗留

- 文件/目录命名目标：见名知意、统一、可搜索、可维护。命名是给未来的自己和同事看的，不是越短越好。
- 能用常见词汇就用常见词汇
- 优先使用 user、order、file、config、request、response 这类通用英文词

- 文件/目录命名避免自造词和含义不明确的缩写，如 usr、btn、mgr、obj、fx
- 避免 fx、tmp、obj、data、info、mgr、usr、btn 这类含义不明确的缩写。
- 比如 fx 可能是 effects、function、file transfer、fix，别人很难猜。

- 文件/目录：优先使用常见英文名词，小写，按项目约定使用 kebab-case 或 snake_case。
- 例如：user-profile.ts、order-service.ts、user_profile.py。

- 文档命名中文优先
- 生态约定的入口文件保留英文：README.md / CHANGELOG.md / LICENSE
- 设计、规范、说明类：中文名，如 项目详细设计.md、命名规范.md
- 阶段报告：日期-主题.md，如 2026-10-14-前后端打通报告.md
  （ISO 日期便于排序；不要用 p1/p2/p3 —— 含义不明且会随路线图漂移）
- 同一主题前后端各一份时，主题里带端名：自主行为前端报告 / 自主行为引擎报告
- 代码目录与代码文件一律英文（kebab-case / snake_case）

## 变量名缩写（2026-10-26 补充）

- 允许的常见缩写：`id`、`url`、`api`、`ctx`、`req`、`res`、`err`、`msg`、`cfg`；
- 同一模块内必须一致（不能一个文件写 `config`、另一个写 `cfg`）；
- **跨文件导出的名字一律用完整词**（导出 `config`，不写 `cfg`）；缩写只用于局部变量。

## 测试与样式文件命名

- **测试**：`<被测文件名>.test.ts`，与被测文件同目录；不建 `__tests__/` 目录。
- **样式**：跟随业务域，放在该域的 `styles/` 或域根（如 `src/work/styles/work-task.css`）；
  入口文件只做 `@import`，不写具体规则（`src/work/work.css` 即此约定）。

## shared 目录例外

- `shared/` 回答的是「谁用」而不是「放什么」，属于生态通用词，允许使用；
- 但 `shared/` 内部必须按能力命名（`batch-selection/`、`input-history/`、`time.ts`），
  不允许再出现 `utils/`、`helpers/`、`common/`。

未登记的抽象词一律按「禁用抽象名」处理——这是防止「业务术语」变成万能借口的唯一办法。

## 文件名重名与泛名（2026-10-26 补充）

- **同一业务域内文件名不重复**（硬规则）；**跨业务域允许重名**，前提是：
  - 名字在各自域内语义清晰，如 `conversation/format.ts` 与 `task/format.ts`；
  - 跨域只能引用对方对外导出的入口，不直接引用对方内部实现文件；
  - 项目引入路径别名后（如 `@work/conversation/format`），跨域引用必须走别名，不用长相对路径。
- **放进 `shared/` 的文件必须加限定词**：`work-format.ts` 而不是 `format.ts`——共享层被所有域引用，重名会让搜索无法判断来源。
- **禁用泛名文件**：`format.ts`、`utils.ts`、`helpers.ts`、`common.ts`、`misc.ts` 这类名字看不出装了什么，等于没有命名。按实际能力命名：`format-value.ts`、`clipboard.ts`、`link.ts`。
- **一个文件只做一类事**：出现「时间格式化 + 剪贴板 + 外链打开」混在一个文件时，按能力拆开。
- **禁用抽象名、隐喻名、架构角色名**（默认规则，不是绝对禁止）：`hero`、`flow`、`status`、`bridge`、`shell`、`core`、`engine`、`manager`、`service`、`handler`、`helper` 这类名字回答的是「它在架构里扮演什么角色」，而不是「这里放的是什么业务」。
  - **优先级：框架/生态已有约定 > 本规则**（沿用本文档开头的「工具强制 > 生态惯例 > 本规范 > 历史遗留」）。NestJS 的 `*.service.ts`、Angular 的 `*.guard.ts`、Electron 的 `main.ts` / `preload.ts`、Monorepo 的 `packages/core/`、框架官方 API 名（如 `contextBridge`）一律照生态约定，禁用清单只在**没有生态约定**时生效。
  - 本项目不依赖上述框架的强制命名，新文件默认遵循禁用清单；确需使用禁用词时，必须在目录 README 或文件首行注释里说明理由。
  - ✗ `status/`（什么状态？）→ ✓ `model-status/`（模型与余额状态）
  - ✗ `flow/`（什么流？）→ ✓ `agent-flow/`（Agent 执行步骤流）
  - ✗ `bridge/`（桥接什么？）→ ✓ `work-mode/`（工作模式接线）
  - ✗ `hero/`（主视觉区）→ ✓ `new-task/`（新建任务）
- **判断方法**：把目录名单独给一个没参与开发的人看，他能说出里面放什么吗？说不出就是抽象名。
- **业务术语例外**：`agent`、`bubble`、`memory` 这类已经在本项目里形成稳定业务含义的词可用，但新增术语必须在首处注释里解释。
- 以上规则**目录名和文件名同样适用**。
- 例外：`index.ts` / `main.ts` / `types.ts` 属生态约定，允许存在；不同业务目录下的同名入口不视为重名。
- 存量文件按同一规则逐步整理，新文件必须遵守。
