# 高内聚（High Cohesion）——后端代码组织原则

## 1. 一句话定义

**高内聚**：一个模块、包、目录、类或函数，只围绕一个明确职责，把相关的东西放在一起，边界清晰，修改时只影响局部。

通俗说：

> 相关的东西放一起，一个模块只做一类事，改它不用到处跑。

后端的高内聚，不只是“代码放一起”，还包括：

- 业务规则集中；
- 数据所有权清晰；
- 模块间依赖明确；
- 改一个业务只进一个模块。

---

## 2. 为什么重要

项目小的时候，怎么放都还能找到。  
项目变大、模块变多、多人协作后，低内聚会直接导致：

- 改一个功能要跳 Controller、Service、Dao、Entity 多个目录；
- 同一业务代码散落各处，边界模糊；
- 删除功能不敢删，不知道谁还在引用；
- 全局 `controller/`、`service/`、`dao/`、`utils/` 变成垃圾桶；
- 新人看不懂业务边界；
- 模块无法独立测试、拆包、拆服务、拆库；
- 数据被多个模块随意读写，最终变成“大泥球”。

高内聚的目的不是“文件好看”，而是：

> **让业务边界清晰，让修改局部化，让协作可预测，让系统可演进。**

---

## 3. 判断标准

一个后端模块/包是否高内聚，可以用这几个问题检查：

1. 能否用一句话说清它的职责？
2. 跟这个业务相关的接口、用例、领域模型、仓储实现，是否都在同一个模块内？
3. 改这个业务，是否只需要进一个模块？
4. 删除这个业务，是否敢整模块删除？
5. 它是否拥有自己的数据表/Schema，并且只由自己写入？
6. 是否把业务逻辑塞进了全局 `utils/`、`common/`、`base/`？
7. 跨模块共享的代码，是否真的被多个模块使用？
8. 模块之间是否直接访问了对方的内部实现或数据库？
9. 模块之间是否通过明确接口或事件通信？

如果答案大多是“是”，就是高内聚。  
如果答案大多是“否”，就是低内聚。

---

## 4. 正例

按业务域垂直切分，域内自包含：

```text
modules/
  ├── order/
  │   ├── interfaces/          # 入站适配器
  │   │   ├── http/            # Controller / Handler
  │   │   ├── rpc/             # RPC 接口
  │   │   ├── consumer/        # MQ 消费者
  │   │   └── job/             # 定时任务
  │   ├── application/         # 应用层：用例编排
  │   │   ├── OrderAppService
  │   │   ├── dto/
  │   │   └── assembler/
  │   ├── domain/              # 领域层：核心业务
  │   │   ├── Order             # 实体/聚合根
  │   │   ├── OrderRepository   # 仓储接口
  │   │   ├── events/
  │   │   └── services/
  │   └── infrastructure/      # 基础设施层
  │       ├── persistence/      # 仓储实现、ORM
  │       ├── clients/          # 外部 API 客户端
  │       ├── mq/               # 消息实现
  │       └── cache/
  ├── payment/
  ├── inventory/
  └── user/
```

优点：

- 订单相关的接口、用例、领域模型、仓储实现全在 `order/`；
- 改订单只进 `order/`；
- 删除订单可以整模块删；
- 其他模块不受影响；
- `order/` 拥有自己的表，别人不能直接写；
- 模块之间通过接口或事件通信。

## 5. 反例

按技术类型全局铺开，同一业务被打散：

```text
controllers/
  OrderController
  PaymentController
  UserController
services/
  OrderService
  PaymentService
  UserService
daos/
  OrderDao
  PaymentDao
  UserDao
entities/
  Order
  Payment
  User
utils/
  order-utils
  payment-utils
```

问题：

- 订单的 Controller、Service、Dao、Entity 散落各处；
- 改一个订单功能要跳多个目录；
- 删除订单不敢删，因为不知道哪些文件还有引用；
- 全局目录越来越像垃圾场；
- 业务边界完全看不出来；
- 无法拆库、拆服务、独立部署；
- 数据被多个 Service 随意读写，最终失控。

## 6. 后端分层：模块内怎么放

高内聚不是把所有东西堆进一个超大文件，也不是禁止分层。

正确理解是：

> **同一职责集中，不同职责分离。**

后端推荐模块内部按四层组织：

```text
interfaces/       入站适配器：HTTP、RPC、MQ、Job
application/      应用层：用例编排、事务边界
domain/           领域层：实体、值对象、领域服务、仓储接口
infrastructure/   基础设施：持久化、外部客户端、消息、缓存
```

依赖方向必须遵守：

```text
interfaces -> application -> domain
infrastructure -> domain（实现 domain 定义的接口）
```

核心规则：

1. **domain 层不依赖框架、数据库、HTTP、MQ。**
2. **application 层只做用例编排，不写核心业务规则。**
3. **infrastructure 层实现接口，不反向依赖上层。**
4. **interfaces 层只做协议转换，不写业务逻辑。**
5. **模块内部可以继续按技术分层，但业务域边界必须优先。**

例如 `order/` 内部继续变大，可以这样：

```text
order/
  ├── interfaces/
  ├── application/
  ├── domain/
  ├── infrastructure/
  ├── shared/          # 仅 order 模块内部共享
  └── types/
```

这是“模块间高内聚，模块内按职责分层”。

---

## 7. 模块之间：边界怎么定

模块之间必须遵守以下规则：

1. **每个模块拥有自己的数据表/Schema**
   - `order` 模块只能直接查自己的表。
   - 不能直接 `join` 别的模块的表。
   - 不能跨模块写数据库。

2. **模块之间通过接口或事件通信**
   - 同进程：模块暴露 `OrderAppService` 接口。
   - 跨进程：HTTP / RPC / MQ 事件。
   - 禁止绕过接口直接调对方内部实现。

3. **共享代码只放真正跨域通用的东西**
   - 认证、日志、错误码、工具类放 `shared/`。
   - 业务逻辑绝不往 `shared/` 塞，否则它会变成垃圾场。

4. **默认模块化单体，按需拆微服务**
   - 不要一上来就微服务。
   - 微服务带来分布式事务、网络故障、运维复杂度、链路追踪、数据一致性等一系列问题。
   - 没有足够痛的拆分理由，就不要拆。
   - 拆分必须按业务域拆，不是按 `controller/service/dao` 拆。

---

## 8. 数据与事务

后端高内聚的核心难点之一就是数据。

- **单模块内**：用本地事务。
- **跨模块**：不要用分布式事务硬扛。用：
  - 事件驱动；
  - Outbox 模式；
  - Saga 补偿；
  - 最终一致性。
- **读多写多**：可引入 CQRS，读写模型分离。
- **跨模块查询**：建读模型，或通过 API 组合，不要直接 join 对方表。

一句话：

> **谁的数据谁负责，别人只能通过接口拿。**

---

## 9. 落地原则

团队统一遵循以下原则：

1. **业务代码优先按业务域垂直切分**
   - `modules/order/`
   - `modules/payment/`
   - `modules/inventory/`

2. **模块内部再按职责水平分层**
   - `interfaces/`
   - `application/`
   - `domain/`
   - `infrastructure/`

3. **只被一个业务域使用的代码，放业务域内部**
   - 例如订单专用校验规则放 `order/domain/`。

4. **被多个业务域复用的代码，才放 `shared/`**
   - 例如通用 `Result`、`ErrorCode`、`IdGenerator`、`Clock`。

5. **禁止把业务逻辑塞进全局 `utils/`、`common/`、`base/`**
   - 全局目录只放真正跨域通用的能力。

6. **模块之间通过明确接口通信**
   - 不直接访问对方内部实现；
   - 后端通过应用服务/接口/事件；
   - 前端通过导出的入口组件/函数；
   - C++ 通过头文件暴露的接口。

7. **共享代码下沉原则**
   - 只被一个业务域用 → 业务域内部；
   - 被多个业务域用 → `shared/`；
   - 被全公司/多项目用 → 独立基础库/包。

## 10. PR / 架构评审检查清单

评审时可以直接问：

- 这个类/文件为什么放在这里？
- 它只被谁使用？
- 是否应该下沉到业务域内部？
- 是否应该上浮到 `shared/`？
- 改这个功能需要动几个模块？
- 删除这个功能是否敢整模块删？
- 是否把业务逻辑放进了全局 `utils/`、`common/`、`base/`？
- 模块之间是否直接依赖了对方内部实现？
- 模块之间是否直接访问了对方数据库？
- 数据所有权是否清晰？
- 共享代码是否真的被多个模块使用？
- 跨模块事务是否使用了最终一致性方案？

---

## 11. 总结

**高内聚 = 相关的东西放一起，一个模块只做一类事，改它不用到处跑。**

落到后端工程上就是：

> **业务域垂直切分，模块内部按职责分层；**  
> **业务代码放业务域，通用代码放 shared；**  
> **谁的数据谁负责，模块间只通过接口或事件通信；**  
> **改一个功能只进一个模块，删一个功能敢整模块删；**  
> **默认模块化单体，按需拆微服务。**

这是前端、后端、C++ 项目都通用的代码组织原则。后端只是多了数据所有权、事务边界和模块通信的约束。
